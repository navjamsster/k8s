# Cluster Migration: kube-apiserver Connection Issue

## Problem Statement
After a cluster migration, the `kube-apiserver` on the controlplane is not starting. The issue is that the apiserver was incorrectly pointed to the etcd **peer port 2380** instead of the correct **client port 2379**.

### Key difference:
- **Port 2379**: etcd client API (used by apiserver and clients)
- **Port 2380**: etcd peer communication (inter-node etcd cluster communication only)

## Initial setup - Breaking the cluster

This script demonstrates the issue:

```bash
# Backup the working manifest
cp /etc/kubernetes/manifests/kube-apiserver.yaml \
   /tmp/kube-apiserver-working.yaml

# Inject the bug — change 2379 to 2380
sed -i 's|https://127.0.0.1:2379|https://127.0.0.1:2380|g' \
  /etc/kubernetes/manifests/kube-apiserver.yaml

# Wait for apiserver to crash (~30 seconds)
watch crictl ps -a | grep apiserver
# → Should show Exited or CrashLoopBackOff

# Verify the cluster is broken
kubectl get nodes
# → "connection refused" ✅
```

## Solution

### 1. Verify the broken state

```bash
kubectl get nodes
# → connection refused to server controlplane:6443
```

Check container status:

```bash
crictl ps -a | grep apiserver
# → Shows Exited or CrashLoopBackOff
```

### 2. Review the error logs

Get the container ID and check logs:

```bash
crictl ps -a | grep apiserver
# Note the container ID

crictl logs <container-id> 2>&1 | tail -20
```

Expected error output:

```
dial tcp 127.0.0.1:2380: connect: connection refused
failed to create listener: error listening on 127.0.0.1:2380
context deadline exceeded
```

> This confirms the apiserver is trying to reach etcd on port 2380, which is not listening.

### 3. Verify etcd client port

Check the etcd manifest to confirm the correct client port:

```bash
cat /etc/kubernetes/manifests/etcd.yaml | grep "listen-client"
# Expected: --listen-client-urls=https://127.0.0.1:2379
```

### 4. Fix the kube-apiserver manifest

Backup the broken manifest:

```bash
cp /etc/kubernetes/manifests/kube-apiserver.yaml \
   /tmp/kube-apiserver-broken.yaml
```

**Option A — Using sed (fastest for exam):**

```bash
sed -i 's|https://127.0.0.1:2380|https://127.0.0.1:2379|g' \
  /etc/kubernetes/manifests/kube-apiserver.yaml
```

**Option B — Using vi (more control):**

```bash
vi /etc/kubernetes/manifests/kube-apiserver.yaml
# Find: --etcd-servers=https://127.0.0.1:2380
# Fix:  --etcd-servers=https://127.0.0.1:2379
```

### 5. Verify the fix

```bash
grep "etcd-servers" /etc/kubernetes/manifests/kube-apiserver.yaml
# Expected: --etcd-servers=https://127.0.0.1:2379
```

> The `--etcd-servers` flag must point to the **client port 2379**, not the peer port 2380.

### 6. Restart the kubelet to reload manifests

```bash
systemctl restart kubelet
```

Wait for apiserver to come back up (~30-60 seconds):

```bash
crictl ps -a | grep apiserver
# → Should show Running

watch kubectl get nodes
# → controlplane   Ready   control-plane
```

### 7. Verify cluster health

```bash
kubectl get nodes
# → controlplane   Ready

kubectl get pods -n kube-system
# → All pods should be Running
```

## Additional diagnostics

After fixing the main issue, check for secondary problems:

### Check 1 — High CPU usage on controller-manager

```bash
kubectl get pods -n kube-system | grep controller
crictl logs $(crictl ps -a | grep controller | awk '{print $1}') 2>&1 | tail -10
```

If CPU is too high, edit the manifest:

```bash
vi /etc/kubernetes/manifests/kube-controller-manager.yaml
# Reduce CPU request if too high: resources.requests.cpu: "4" → "200m"
```

### Check 2 — High CPU usage on scheduler

```bash
vi /etc/kubernetes/manifests/kube-scheduler.yaml
# Reduce CPU request if needed
```

### Check 3 — Wrong IP address format

```bash
grep "etcd-servers" /etc/kubernetes/manifests/kube-apiserver.yaml
# If using wrong IP (e.g., 192.x.x.x instead of 127.0.0.1):
# Fix to: --etcd-servers=https://127.0.0.1:2379
```

## Summary

| Issue | Solution |
|-------|----------|
| apiserver pointing to port 2380 (peer port) | Change to port 2379 (client port) in `--etcd-servers` flag |
| Connection refused errors in logs | Verify etcd is listening on 2379 with `netstat -tlnp\|grep etcd` |
| apiserver stuck in CrashLoop | Restart kubelet after fixing manifest: `systemctl restart kubelet` |
